## Pilot research question and result

The pilot question was whether a ChatGPT turn, including its provenance, could be reconstructed from a Windows full-RAM image without taking a V8 heap snapshot, and which client states defeated that reconstruction. **Visible-response development images showed feasibility:** bounded stream records in user-space pages of `ChatGPT.exe` renderers yielded one complete turn with v1 and two separate complete turns with a revised v2 joiner. The unchanged v2 method then reconstructed one exact turn on a **fresh visible-response image**. All prompt, answer, conversation-ID, and user/assistant-ID fields matched post-capture ground truth; RAM-derived user times fell within submission windows. This prospective v2 check did not have a clean VM reset or ground truth outside the guest, so it is not independent validation under the supplied protocol. On a fresh close-tab image, unchanged v2 found **zero complete records or candidate turns** across four active renderers, though exact strings and IDs remained somewhere in physical RAM. A fresh navigated-away v2 image likewise yielded zero complete records/candidates across nine active renderers. Exact prompt, response, and message IDs appeared in raw physical RAM, but not in those mapped active renderers. An earlier navigated-away image was also negative under frozen v1. These are method failures in non-reset states, not proof of erasure or general failure rates. The first navigated-away pilot remains inconclusive because investigator-created copies contaminated its strings hits.

The research question preceded the CATF challenge, which later became a practical application of the same provenance problem. The challenge image was not used as held-out validation. The pilot captures were made September 16–17; the September 29–30 follow-ups were also post-CATF.

## RAM analysis and result

[scan_pilot.py](scan_pilot.py) searched the **known** synthetic marker, response, and UI-observed IDs as ASCII and UTF-16LE in a streaming pass. It was deliberately a strings baseline, not the proposed reconstruction method. Counts include 368 ASCII prompt-marker hits, 302 exact ASCII response hits, 555 ASCII final-conversation-ID hits, 140 ASCII user-message-ID hits, and 141 ASCII assistant-message-ID hits. Counts alone are not field recovery: the same strings appeared in copies made by the investigator.

[classify_pilot_contexts.py](classify_pilot_contexts.py) examined 368 prompt-marker surroundings. Its coarse automated labels were: 22 DOM-capture copies, 97 ground-truth copies, 111 Codex tool/transcript copies, 137 unclassified, and one record-like unattributed. Manual inspection showed that the sole record-like sample was another Codex JSON-RPC tool record; sampled “unclassified” hits included accessibility text, tool output, the prompt command, and the ground-truth patch. The classifier is heuristic and did not establish provenance for all 368 hits. An exact-marker search of `C:\Users\Win10\.codex\sessions\2026\09\16` also found this active Codex session transcript, independently confirming local-file contamination.

**Field score from RAM:** unassessed for History conversation ID, prompt, response, submission/assistant IDs, timestamps, and their join. The strings baseline was given those values as input. There is no defensible complete, partial, or absent *blind reconstruction* score for this pilot. In particular, “not attributed” does not mean the original renderer pages were erased.

## Second pilot: visible response and bounded-record parser

The second trial is documented in [its ground truth](trial_iab_visible_002/ground_truth.json). Its synthetic prompt was generated inside the browser-control runtime and was not printed to the Codex transcript before capture; ground truth was written **after** capture. The browser-control runtime may still have held a copy, and a provisional `WEB:` conversation ID was inadvertently printed in a structural control output before capture. This VM had not been reset. The ground-truth file records the exact prompt, actual response, URL and DOM IDs, and action times.

| Event | UTC evidence |
| --- | --- |
| Prompt submitted in signed-in Chat mode | `17:25:20.316`–`17:25:20.539` |
| Completed response observed, still visible | `17:25:38.283` |
| Sparse raw physical-memory acquisition | `17:25:46.6283871`–`17:25:59.4432062`; WinPmem log: 12.645203 seconds of imaging |
| Raw image | 18,253,611,008 logical bytes, SHA-256 `C91CF60D657A178BC51DAC63A4C8C37D4D12C6ABE4F817E241C657A9137DB765`; hash rechecked after moving the file |

Volatility 3 `windows.info` recognized the raw image and reported in-image time `17:25:46+00:00`. `windows.pslist` and `windows.cmdline` completed on this raw image. The first candidate renderer, PID 7608, produced an apparent all-field hit only because its process map included **shared kernel virtual pages**. The all-address-space scan's 217 known-marker hits were all in kernel space. A corrected scan of PID 7608's 7,179 user-space map rows found zero supplied markers. The larger `ChatGPT.exe --type=renderer` PID 8336 had 71,034 user-space rows; its user-space pages contained the prompt, response, conversation ID, and both message IDs. This is process-scoped evidence, though it does not prove the process held no copies from browser-control instrumentation.

The [blind pilot parser](trial_iab_visible_002/parse_stream_items.py) scans mapped user-space bytes for complete `{"type":"stream-item"...}` JSON objects, decodes each bounded `encoded_item` server event, and receives **no known prompt, response, IDs, or offsets**. It found 47 syntax hits and 30 unique complete records. The [joiner](trial_iab_visible_002/reconstruct_turns.py) uses conversation/turn IDs and `parent_stream_item_id` ancestry. It accepts a turn only when a user input record leads to an assistant message, a response-content patch, a matching assistant marker, and a stream-completion event. On this development image it emitted **one** candidate.

Post-capture [scoring](trial_iab_visible_002/result_redacted.json) found exact matches for the prompt, actual response (`red, green, blue`), conversation ID, user message ID, and assistant message ID. The RAM-derived user creation time `17:25:20.445Z` falls inside the submission interval. The assistant creation time `17:25:21.491998Z` precedes the completed-response observation; it is a message-start time, **not** evidence of when the answer finished. The supporting bounded-record SHA-256 values and stream IDs are in the redacted result. The parser and joiner were then frozen at the hashes in [FROZEN_METHOD.json](FROZEN_METHOD.json).

The frozen parser expects this observed compact JSON signature and a complete record in virtually adjacent resident pages. Other serialization, fragmented records, or nonresident pages can produce a false negative. Its recorded per-record digest slices original bytes using a decoded-character count; for any record containing unescaped multibyte UTF-8 before the end, that digest may omit trailing bytes. Those digests identify the pilot's extracted records but have not been independently reverified since the second image and private extracts were removed. A corrected digest and a separately retained synthetic-record fixture are needed before a reproducibility claim.

## Third pilot: frozen method after navigation away

The third trial's [acquisition manifest](trial_iab_away_003_results/acquisition.json), ground truth, frozen-run manifest, scripts, and [redacted score](trial_iab_away_003_results/result_redacted.json) are preserved. The prompt was generated and sent without printing its exact value in the Codex transcript before capture. The completed response was observed at `17:52:20.485Z`; the tab navigated to Example Domain at `17:52:28.686`–`17:52:29.402Z`. WinPmem captured a new default-sparse raw image at `17:52:35.8257002`–`17:52:50.5812999Z` (14.653620 seconds of imaging), SHA-256 `E15D63627D6610B3D873330BB367BE152D1EA174FA50C23DCCFC3403DDA218B9`. After acquisition, browser Back revealed the actual response `Mercury|Venus|Earth`, final conversation URL ID, and both DOM message IDs; [ground_truth.json](trial_iab_away_003_results/ground_truth.json) records them. This was the same VM without a restore.

Volatility 3 recognized the image and reported in-image time `17:52:36+00:00`. Image-derived `windows.pslist` and `windows.cmdline` selected **all seven active** `ChatGPT.exe --type=renderer` processes, without looking at the known prompt or answer. The frozen parser and joiner hashes were checked against the manifest before execution. Across those seven user-space maps, the parser saw 18 syntax signatures, **zero complete stream-item records**, and **zero candidate turns**. The former visible-state renderer PID 8336 was absent from both `pslist` and a later `psscan`. This is an **absent reconstruction by the frozen method on one non-reset trial**, not evidence that the turn was erased.

An explicitly **unfrozen exploratory** scan over all 18,253,611,008 physical bytes saw 230 stream-item signatures but no complete JSON object. A heuristic context check labeled 206 as code/log-like, 15 as record-like, and nine unclassified; all 15 record-like fragments contained the **previous visible pilot's** conversation ID, and none contained the current away-trial ID. This is direct evidence of cross-trial residue in a VM that was not reset. The separate [known-marker baseline](trial_iab_away_003_results/known_marker_baseline.json), given the actual values after capture, found 114 exact ASCII prompt hits, 154 exact ASCII answer hits, 949 ASCII conversation-ID hits, 15 user-message-ID hits, and 12 assistant-message-ID hits in raw physical memory. Those counts have **no process provenance or bounded join**; the browser-control runtime and other investigator processes may have held copies. They establish that failure of the frozen parser cannot be equated with removal of all trial strings from RAM.

A further **post-hoc known-value scan** of the seven active renderer user-space maps found zero exact prompt, answer, user-ID, or assistant-ID hits in every renderer, while the conversation ID appeared 46 times across three renderer maps (3, 31, and 12 hits). [The per-process result and script](trial_iab_away_003_results/known_marker_mapped_renderers.json) are separate from the frozen method. This per-row scan can miss a value split across mappings; shared pages and a conversation ID alone do not attribute a complete turn or locate the raw-image strings found elsewhere.

## Fourth pilot: two distinct conversations and a revised joiner

The fourth trial's [acquisition manifest](trial_iab_two_chats_004_results/acquisition.json) and shareable results cover two synthetic conversations created in separate signed-in in-app tabs. Both responses were visibly complete before capture. The prompts were generated inside the browser-control runtime and withheld from Codex output until after acquisition. The first prompt was submitted at `18:35:11.537`–`18:35:11.819Z`, with completion observed at `18:35:55.113Z`; the second was submitted at `18:36:19.002`–`18:36:19.297Z`, with completion observed at `18:37:07.200Z`. WinPmem acquired the default-sparse raw image at `18:37:16.0061134`–`18:37:30.3157067Z`, 18,253,611,008 logical bytes, SHA-256 `8BE3FCA651B37248E0161C7ECD52790B049565E98016F478982AA6DB34D2B2EE`. Post-capture DOM/URL checks recorded both actual answers and IDs in [ground_truth.json](trial_iab_two_chats_004_results/ground_truth.json). This was another image from the same non-reset VM.

The unchanged frozen v1 method selected all eight active `ChatGPT.exe --type=renderer` processes from the image's process list and command lines. Six older renderers had no complete records. The two renderers created for the new tabs yielded **20 complete bounded records each**, but **zero v1 candidate turns**. [The v1 run manifest](trial_iab_two_chats_004_results/frozen_run_manifest.json) and [redacted score](trial_iab_two_chats_004_results/result_redacted.json) preserve that failure. Inspection showed that each synthetic user message and its ID were in a parsed `v.message` event; v1's joiner accepted user messages only in `input_message` events. This was a joiner format gap, not absence of user bytes. A separate ground-truth-assisted [per-renderer string baseline](trial_iab_two_chats_004_results/known_marker_mapped_renderers.json) found each chat's exact prompt and IDs in mapped pages of its new renderer. These known-value counts are not the reconstruction method.

I copied the v1 joiner, added user-role handling for `v.message`, and kept the bounded parser and its assistant/patch/marker/completion ancestry checks. This [v2 joiner](method_v2/reconstruct_turns.py), developed **on the fourth image**, produced one candidate from each new renderer. [Post-hoc v2 scoring](trial_iab_two_chats_004_results/result_v2_redacted.json) found all five exact fields matched for each chat, both RAM user times fell inside their submission intervals, both assistant-start times preceded completed-response observations, and no ambiguous user ancestor or cross-chat candidate appeared. The result is evidence that the observed record format supports two correctly linked turns in this image; **it is not an independent false-join rate or held-out validation**. The v2 parser/joiner hashes were frozen at `18:57:10Z` in [FROZEN_METHOD_V2.json](FROZEN_METHOD_V2.json), before any fifth capture.
